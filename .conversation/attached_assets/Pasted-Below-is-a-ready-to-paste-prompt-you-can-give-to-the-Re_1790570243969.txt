 ## 1\. Application Objective

 Build a task-management web application where users can:

 - Create tasks with a task description/name, date, and time.
- Schedule tasks for future execution/reminders.
- See scheduled, upcoming, and completed tasks from a dashboard.

- Click any task to view its details.

- Delete a task.
- Mark tasks as completed.
- See live HTTP status/response information on the webpage.
- Run a background job queue/scheduler so scheduled tasks are processed automatically.
- Deploy the completed application so it is accessible through a live public URL.

 Use clean, maintainable code and organize the project as a real Flask application rather than putting everything into one Python file.

 # 11\. Background Job Queue / Scheduler

 This is a critical requirement.

 Implement a background scheduler/job queue that monitors scheduled tasks.

 When a task is created:

```
User creates task
        ↓
Save task to SQLite
        ↓
Create scheduler/job entry
        ↓
Wait until scheduled date/time
        ↓
Execute reminder job
        ↓
Notify browser/user
        ↓
Update task state
```

 Use a Python scheduling/background-job solution that is compatible with Flask deployment.

 Possible implementation:

 - APScheduler or another lightweight Python scheduler.

 Do not use a scheduler that requires a separate complex infrastructure unless necessary.

 The scheduler must:

 - Load pending scheduled tasks when the application starts.
- Schedule newly created tasks immediately.
- Remove/update jobs when tasks are deleted/rescheduled/completed.
- Avoid duplicate jobs.
- Recover scheduled jobs after application restart by loading them from SQLite.
- Handle exceptions without crashing the Flask application.

 Important:

 The database must remain the source of truth. Do not rely only on in-memory scheduler state.

 # 27\. Production Scheduler Consideration

 Pay special attention to the scheduler during deployment.

 A common deployment problem is that a background scheduler inside a web process can create duplicate scheduler instances when multiple worker processes are used.

 Design the deployment so that:

 - Only one scheduler instance handles scheduled jobs.
- Duplicate reminders are prevented.
- Restarting the application does not create duplicate jobs.
- Existing pending tasks are recovered from SQLite.
- The application continues functioning after restart.

 If the chosen Replit deployment architecture requires a different scheduler strategy, adapt the implementation accordingly while preserving the required behavior.
